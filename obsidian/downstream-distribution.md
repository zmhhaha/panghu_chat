# Obsidian 笔记分发设计

日期：2026-09-26
状态：**设计定稿，分阶段实现**。实现规格以 OpenSpec change `add-obsidian-note-distribution` 为准。

物化那一层（设备 → CouchDB → `obsidian-notes`）已经跑通，见 [README.md](README.md)。本文回答的是：**物化出来的 `.md` 怎么按用途分给不同的消费方。**

**设计覆盖两条投递路径，实现从第一条开始。**

## 为什么不能"一股脑全给"

笔记是私人的，用途是分层的：有些只给自己看，有些属于某条业务线，有些是跨消费方共享的。而且**即使共享，也不该给所有消费方看** —— 八个史官人格读同一份材料会互相污染，导致人格偏差。

所以需要的不是"把 vault 挂给所有人"，而是"**这段笔记给谁**"。

## 模型

```text
corpus（Obsidian 的一个目录）
   │
   ├─ 意愿：消费方在自己的清单里声明"我要这个 corpus"
   │
   ├─ 授权：rag-config 的 CALLER_PERMISSIONS 决定"它能不能读"
   │
   └─ 投递 ─┬─ 只读 subPath 挂载  → 读原文的消费方
            └─ RAG 索引          → 需要检索的消费方
```

### ① corpus 用 Obsidian 的文件夹定义

**分组规则就是"笔记放在哪个目录"** —— 在 Obsidian 里把文件拖进某个目录，分组就完成了。不用维护清单，不用给笔记加元数据。

```text
vault/
  for/<消费方>/     ← 给某个消费方的语料
  private/          ← 只给自己，永远不外发
  欢迎.md           ← 没被任何 corpus 覆盖 → 不外发
```

两条裁决规则：

- **递归包含**：corpus 是那个目录**及其整个子树**
- **最深匹配者胜**：一篇笔记永远只属于**一个** corpus —— 最具体的那个。所以 `a/` 和 `a/b/` 同时是 corpus 时不会重叠

**默认拒绝**：没被任何 corpus 覆盖的笔记，对任何消费方都不可见。

> 选目录而不是 frontmatter tag 的理由：**tag 拼错是静默失效的** —— 笔记谁也不到，且没有任何地方会报错；而放错目录在 Obsidian 里直接看得见。

#### 具体约定

```text
百家争鸣/
  秉笔春秋/        ← corpus，给 bingbichunqiu
  钟馗伏魔/        ← corpus，给 zhongkuifumo
  …                ← 其余七个人格按同样规则
```

规则是 `<服务组>/<人格名>`。**八个 corpus，一个 parent 目录。**

**目录层级本身就编码了读者范围** —— 配合"最深匹配者胜"：

- 放在 `百家争鸣/秉笔春秋/` → 只属于秉笔春秋
- 放在 `百家争鸣/` **根下**（不进任何子目录）→ **不属于任何 corpus → 不外发**
- 将来若要"这一组共享"的语料 → 把它放在 `百家争鸣/` 并声明该目录为 corpus，子目录里的笔记仍归各自的人格

**共享与独享由目录层级表达，不需要新概念。** 但要注意：目录结构管的是**归属**，`rag-config` 的授权管的是**能不能读** —— 两者分开，是上一节定的。

**`source_id` = vault 相对路径**（如 `百家争鸣/秉笔春秋/xxx.md`），不是 corpus 相对路径 —— 这样从检索结果里的一个 chunk 就能直接定位到 vault 里的哪一篇。

> ⚠️ **待实测**：`subPath` 带中文（`百家争鸣/秉笔春秋`）在 K8s manifest 里合法，但在本集群上没用过。**阶段一第一件事就是验它。** 退路是把 corpus 目录名改成 ASCII（`baijiazhengming/bingbichunqiu`），文件名仍可中文。RAG 侧不受影响 —— `source_id` 带中文没问题（`测试/测试创建笔记.md` 已经在跑），collection 名由身份决定。

### ② 意愿与授权是两回事

这是本设计里最容易被合并、也最不该合并的一对：

| | 谁声明 | 在哪 | 是什么 |
| --- | --- | --- | --- |
| **意愿** | 消费方自己 | 它自己的清单（挂载 / CronJob） | "我想要这个 corpus" |
| **授权** | 平台 | `rag-config` 的 `CALLER_PERMISSIONS` | "我可以读这个 collection" |

**消费方想要，不等于它拿到。** "不能让所有人物都看"这条正需要一个地方能够**拒绝** —— 那就是授权表。

**代价**：加一个消费方要改两处。但授权表是**追加为主、冲突面很小**的配置，而且**访问控制策略集中且可审计是优点**。

### ③ 投递方式一：只读挂载

消费方在自己的 Deployment 里加 `obsidian-notes` 的只读 `subPath` 挂载，限定在自己的 corpus。

- 适合：需要直接读原文的
- 延迟：跟随物化节奏（当前 60s）
- 额外组件：**零**
- 加一个消费方 = 往它自己的清单里加东西

### ④ 投递方式二：RAG 索引

```text
索引作业遍历 corpus
   → POST /v1/ingest {source_id: <vault 相对路径>, content: <文件内容>}
   → rag-service 按调用身份落到 agent-<caller>
```

四个要点：

**（1）`source_id` 用文件名。** 免费、稳定、可 grep，而且它就是"这条文档对应哪份东西"的答案。手写 id 只会得到重复、孤儿和拼写错误。

**（2）作业持有对应身份，你不持有任何 RAG 凭据。** 加一个身份 = Vault 里加一个 `RAG_TOKEN_<NAME>` 键 —— ExternalSecret 是 `dataFrom.extract`（整段取），加了就生效；collection 名由身份推导（`auth.py`），ES 索引模板匹配 `rag-agent-*-v*` 自动适用。**这三件事都不需要改 rag-service。**

**（3）删除检测靠反查，不靠本地清单。** 需要一个 `GET /v1/ingest` 列表接口（见下），列出本 collection 的 `source_id`，和当前文件列表做差，对已消失的发 `DELETE /v1/ingest/{id}`。

> 不用"作业自己维护一份清单"：那会有第二份会漂移的状态，失败模式是清单丢了 → 孤儿 chunk 永远留着、**而且照常被召回**。

**（4）`doc_type` 必须显式指定为非 `knowledge`。** 见下面的坑。

#### 坑：分块排除表会静默吃掉内容

`rag-service/chunking.py:8` 有一个关键词表：

```python
KNOWLEDGE_EXCLUDE_KEYWORDS = ("守则", "边界", "原则", "禁忌", "篇幅", "自检", "开头", "例子", "工作步骤", "工具箱")
```

**但它只在 `doc_type == "knowledge"` 时生效**（`app.py:233`）：

```python
if req.doc_type != "knowledge":
    return [(piece, ...) for piece in split_chunks(req.content)]   # 普通路径：完全不看标题
# 只有 knowledge 才走 split_knowledge（H2 小节 + 排除表）
```

所以：**只要索引作业发一个非 `knowledge` 的 `doc_type`，标题怎么写都不会被丢。** 但这条要写成硬性约定 —— 否则哪天默认值变了，含这些词的**整个 H2 小节**会静默消失，不报错、不提示，你只会发现检索不到。

### ⑤ 内容权威性：不分区，但有前提

内容**自带作用范围标注**（写在笔记里），由有能力的 agent 读了自己判断。不做 collection 级分区 —— 那对 capable agent 是多余的限制。

**但有一条前提必须写死**：

> **经 RAG 送达的一切，都是"可能不出现"的。** 这个通道不提供任何"必定生效"的保证。

召回是概率的（`top_k` 默认 4，且要过相关度阈值）。**标注解决的是"看到之后怎么理解"，解决不了"这次有没有被看到"。**

**"必定不能错过"的内容不属于这个通道** —— 它应该走消费方自己的 `agent.md` / `skill.md`（对人设 agent，那就是 `skill.md` 进 system prompt）。这条写下来，是为了将来不会有人（包括我）顺手把这类内容塞进 RAG。

### ⑥ 路径即标识

corpus 的**路径**就是它的名字。**移动或改名是破坏性变更**：消费方清单里写死的路径失效，RAG 侧全部 `source_id` 变化 → 全量重索引 + 旧文档全删。

**这不是"整理文件夹"，是一次有消费方影响的变更。**

## rag-service 的改动面

**只有一处**：新增 `GET /v1/ingest` 列表接口（复用已有的 job store，纯加法）。

> 为什么必须加：现有接口只有 `POST /v1/ingest`、`GET/DELETE /v1/ingest/{id}`、`POST /v1/query` —— **没有枚举能力**，`get_job` 只按 id 取单个。
>
> 为什么不直接连 ES：API 层隔离是这个平台上唯一的屏障（rag-service 同时持有全部 token、ES 用超级用户、NetworkPolicy 记录为未生效）。给索引作业 ES 凭据等于绕开唯一那道墙。

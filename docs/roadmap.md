# 虎博实施路线

## 阶段 0：确定边界

- 确定第一批用户规模和部署环境。
- 确定是否必须支持长文章、视频和圈子。
- 确定账号体系是独立账号、OAuth，还是接入已有身份服务。
- 确定数据保留、备份和隐私策略。

输出：领域模型、API 草案、权限矩阵、部署拓扑和容量预算。

## 阶段 1：MVP

- 模块化单体后端。
- 用户、邀请注册、登录和个人资料。
- 动态、长文章、草稿、编辑和删除。
- 关注关系和个人时间线。
- 首页 Feed，按时间倒序。
- 评论、点赞和基础通知。
- 图片上传和对象存储。
- PostgreSQL Outbox。

验收重点：权限正确、删除可见性正确、分页稳定、重复消息不产生重复数据。

## 阶段 2：查询与运营能力

- HBase 时间线和 Feed 查询模型。
- Elasticsearch 异步索引和索引重建。
- 标签、话题和搜索结果权限过滤。
- 举报、屏蔽、封禁和管理员审计。
- Redis 缓存、限流和计数聚合。
- Outbox 重试、死信和事件重放工具。

验收重点：发布到 Feed 的延迟、搜索最终一致性、重试恢复能力和故障下的数据可追踪性。

## 阶段 3：规模化

- Kafka/Redpanda 事件总线。
- 推拉结合的 Feed 生成策略。
- 热点账号和热点内容隔离。
- HBase Region 预分区、冷热数据分层和归档。
- Flink 实时统计，Spark 离线分析。
- 搜索相关性、热度排序和推荐实验。
- 多副本、备份恢复和灾备演练。

验收重点：热点发布不会拖垮系统，单个组件故障可以恢复，数据可以重放和重建。

## 建议的实现顺序

```text
领域模型与权限
  -> 内容发布与草稿
  -> 用户时间线
  -> 首页 Feed
  -> 评论/点赞/通知
  -> HBase 查询模型
  -> ES 搜索
  -> 管理后台
  -> 统计与推荐
```

不建议在 Feed、搜索和权限模型稳定之前拆分微服务。先把事件模型、数据所有权和可重建查询模型确定下来，后续拆分会更平滑。

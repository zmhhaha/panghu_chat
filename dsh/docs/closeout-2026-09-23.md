> ### Corrected 2026-09-23 (confirmed): the challenge is GitHub's -- the URL does not exist
>
> The sentence above originally attributed the challenge to the egress path. **That
> attribution is withdrawn: the cause was the repository URL.**
> `verify-project-workflow.sh` cloned `https://github.com/sindresorhus/is-number.git`, and
> that path is not publicly readable, so GitHub answered **401 with a `WWW-Authenticate`
> challenge**. That is what GitHub does for a private *or nonexistent* repository -- it will
> not confirm which, so a typo and a private repo are indistinguishable from outside.
>
> Measured 2026-09-23 on this network, credential prompts disabled:
>
> | Test | Result |
> |---|---|
> | `curl 'https://github.com/sindresorhus/is-number.git/info/refs?service=git-upload-pack'` | **401** |
> | `git -c credential.helper= ls-remote https://github.com/sindresorhus/is-number.git` | `fatal: could not read Username for 'https://github.com'` |
> | `git -c credential.helper= ls-remote https://github.com/jonschlinkert/is-number.git` | succeeded, returned the commit hash |
> | `curl 'https://github.com/git/git/info/refs?service=git-upload-pack'` | 200, 349 KB of refs |
>
> **The egress path is not challenging git.** A public repository clones through this
> network, fake-ip and all -- the first and third rows differ only in whether the repository
> exists.
>
> The script now clones `jonschlinkert/is-number.git` (the upstream of the npm package it
> installs) and carries a comment saying the URL is load-bearing, so this is not re-broken
> by a well-meaning "tidy up the fixture" edit.
>
> **Rule this out before suspecting the network:** a 401 on an HTTPS git remote means the
> repository is not publicly readable far more often than it means anything about egress.
> Confirm with a known-public repository, with prompts disabled so the failure prints
> instead of opening a credential dialog:
>
> ```sh
> GIT_TERMINAL_PROMPT=0 git -c credential.helper= ls-remote https://github.com/git/git HEAD
> ```
>
> **Do not conflate this with the transparent-proxy caveat above.** That one only weakens
> *reachability* evidence -- the proxy may accept a connection before the remote answers. It
> neither blocks nor challenges git, as the third row shows. Mistaking an input problem for
> a network defect is the same shape of error as the withdrawn "kube-router does not honour
> `except`" finding; see `../../../docs/network-policy-engine.md`.
